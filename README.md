# Swiss Army Knife ML Agent

Type what you are trying to find out and it names the tool and the first move. One private, in-browser tool for regression, classification, clustering, design of experiments (DOE), shelf-life estimation, method-transfer equivalence, variance components and measurement-system analysis, specification setting and study sizing, and sequence optimization, with a built-in academy that teaches every method.

One tool is on screen at a time, and the selector at the top names the **technique**, not one industry's use of it: **Machine learning & design of experiments**, **Linear regression & confidence limits (ICH Q1E)**, **PCA & multivariate SPC (golden batch)**, **Equivalence & non-inferiority testing (TOST)**, **Variance components, ANOVA & Gage R&R**, **Tolerance intervals, power & sample size**, **Genetic algorithms & multi-objective optimization**, **Plasmid & vector selection sandbox**, and **Privacy & data handling**. Each is linkable directly (`#stability`, `#equivalence`, `#variance`, `#limits`, `#sequence`, `#plasmid`).

On the **Where to start** tab, a single **Where this can be used** panel asks once which group you are in and then answers it completely: the jobs that group brings, every method with what it does for *that* group and a button that opens it, a playbook, and the unit operations inside the function. Pick the **modality** (mammalian CHO or microbial *E. coli*) and your **function or group** &mdash; cell line / strain development, upstream PD, downstream PD, AFS, MSAT, GMP manufacturing, QC, QA &mdash; and it lists the **unit operations inside that function**, each with what machine learning is used for at that step: Protein A capture, low-pH viral inactivation and viral filtration for mammalian downstream; cell lysis, inclusion body wash and refolding for microbial. Over 80 unit-operation entries, plus a line per technique per function. The choice follows you between techniques and is held in memory only, so it resets on reload like everything else. The panel opens by default on a desktop, stays folded on a phone, and states plainly that it describes the technique in general, not what this page can read.

Function names and unit operations follow common industry practice rather than any one company's org chart; `applications.js` is plain content and is meant to be edited to match your own site. Inside each tool, panels open only when they earn their place: the practice datasets while nothing is loaded, the settings once there is something to set them for, the DOE builder when the agent has filled it in.

Drop in a CSV &mdash; or a JSON export from a LIMS or an instrument, as a list of records, an envelope with the records inside, one record per line, or one array per column &mdash; and it:

1. **Profiles the data.** It finds numbers, categories, IDs, missing values and correlated inputs.
   - **Carries text columns with many levels.** One-hot encoding cannot carry forty-eight strains or a supplier list: twelve levels get a column each and the rest are lumped into "other". Instead each level is carried as two numbers &mdash; how common it is, and how the result averaged for it, smoothed towards the overall average so a level seen twice cannot claim its own two runs as the truth. Both are rebuilt inside every cross-validation fold, because fitting them once on every row leaks the answers: measured on a column that is pure noise, per fold it honestly scores R&sup2; &minus;0.16, fit once it scores +0.15.
   - **Joins two files on a key.** Load a process log, then a QC report, and it suggests the shared key (BatchID = Batch ID, matched ignoring case and spaces), averages replicate rows (lanes, injections), drops replicate counters, and lists IDs found in only one file before you join. Inner or left join, with undo.
   - **Recognizes column roles.** Analytical results (Purity, Main peak, Titer, Potency, HMW / aggregates, LMW / fragments, impurities), analytical measurements (Retention time, Molecular weight, kDa), record info (Analyst, Lane) and dates are tagged in the profile. The most important result becomes the target, and the other results are set aside as inputs by default so they cannot leak the answer.
2. **Decides the problem type.** A numeric target means regression, a category means classification, and no target means unsupervised (clustering, PCA, outliers). Data that looks like a designed experiment also gets a full DOE effects analysis.
3. **Runs every suitable model with cross-validation** and keeps the simplest one within 0.01 of the top score:
   - Regression: linear, ridge, lasso, quadratic (response surface), k-nearest neighbours, decision tree, random forest, gradient boosting, neural network.
   - Classification: logistic regression, naive Bayes, k-nearest neighbours, decision tree, random forest, gradient boosting (binary), neural network.
   - Neural network (MLP): inputs → 32 → 16 ReLU units → linear or softmax output, trained with Adam and early stopping on 15% held-back rows. Written in plain JavaScript (no TensorFlow.js), so the privacy lock and offline use are unchanged. The learning curve is drawn live while it trains, and a results card explains how it learned. Skipped below 40 rows.
   - Unsupervised: k-means with silhouette-based choice of k, PCA, outlier scoring.
   - DOE: effects, t and p values (or Lenth's method for saturated designs), aliasing, curvature from center points, main-effect and interaction plots, and the best settings.
4. **Explains the result** in plain language, starting with an **In plain English** paragraph above every result &mdash; the finding written so it survives being pasted into an email on its own, before any statistics. It also opens the PDF, so a report forwarded to a manager leads with what was found rather than with a leaderboard. Below it:
   - an **action plan**, such as "Raise Pressure toward 98", "Keep MeltTemp near 217 (sweet spot)" or "Use Resin C, not Resin B", ranked by impact with a confidence level;
   - for categories, a **Target outcome** and **Starting from** selector that re-aims the plan instantly (no re-training), answering questions like "what moves a Bronze customer to Silver or better?" or "how do we keep Gold customers at Gold?". Ranked labels (Bronze < Silver < Gold < Platinum, Low < Medium < High) are treated as "that tier or better";
   - a **what-if mixing desk** right below the plan: one knob per top driver (sliders, or buttons for categories), a live animated prediction with the change versus typical settings, a response curve under each knob that updates with the other knobs, "Apply the action plan" and "Reset" buttons, a warning outside the usual data range, an in-spec badge in Six Sigma mode, and pinned scenarios that carry into the PDF;
   - "how each driver moves the result" curves and a **peek inside the model** (a readable decision tree trained on your data, real trees from the forest or boosting chain, or the recipe of a linear model);
   - a "How to read this" note with an analogy on every chart, linked to the matching lesson;
   - warnings about small samples, gaps, imbalance and overfitting.
5. **Optimizes several results together** (optional, step 2). Pick each result's goal (maximize, minimize or hit a target), its acceptable range and an importance weight. The agent models every result, scores each 0 to 1 (Derringer-Suich desirability), and searches the usual operating range for the best compromise (the highest weighted geometric mean, so no single result is allowed to fail). The results show typical versus best-compromise settings, and the what-if desk shows every result and the overall score live.
6. **Six Sigma & process control mode** (a switch in step 2, off by default). Enter optional spec limits (LSL, USL, target) and get Cp, Cpk, Pp, Ppk, Cpm, Z.bench, expected PPM and sigma level, a histogram against the spec, an I-MR control chart with special-cause signals, box plots by factor, Taguchi signal-to-noise by factor level, and a quality-loss index. Pass/fail targets get defect rate, DPMO and sigma level. Designed experiments are flagged, because their spread is deliberate.
7. **Writes next steps mapped to DMAIC** and pre-fills a **DOE builder** with the drivers it found: full or fractional factorial, Plackett-Burman, central composite or Box-Behnken. It produces a randomized run sheet. Fill in the results, load the sheet back, and the agent analyzes it.

8. **Optimizes DNA sequences by genetic algorithm** (the "Sequence optimizer" tool). Paste a coding sequence and it evolves synonymous codons &mdash; the same protein, spelled differently &mdash; against four goals at once: raise the **Codon Adaptation Index** for CHO, HEK293 or E. coli; hold **GC content** inside a window, overall and in every 50-base stretch; keep the **5' end unfolded** so the ribosome can load; and **remove restriction sites** and long single-base runs, on both strands. It uses NSGA-II (non-dominated sorting, crowding distance, constrained domination), runs in a **Web Worker** so the page stays at full frame rate, and shows the convergence curves, the population diversity and a clickable **trade-off (Pareto) plot** live. The protein is re-translated and checked at the end. Results download as FASTA or a before-and-after CSV.
9. **Estimates shelf life to ICH Q1E** (the "Shelf life" tool). Paste a stability study &mdash; batch, month, result, optionally a storage condition &mdash; set the specification limits, and it fits the degradation trend, runs Q1E's two poolability F tests (equal slopes, then equal intercepts, both at the 0.25 level), and reads the shelf life off the point where the 95% one-sided confidence limit meets the specification. It reports which model the tests chose and why, what each batch would give on its own, and applies Q1E's extrapolation cap (at most twice the data in hand, and never more than 12 months beyond it). Downloads as a Q1E report CSV, and joins the audit package when one is exported.
10. **Tests method-transfer equivalence by TOST** (the "Method transfer" tool). Load results from two labs, instruments or analysts &mdash; either as one file with a method column, or as **a separate file from each lab**, which is how they usually arrive. The two files need not share column names or row order: pick the result column in each, and if both carry a sample identifier the same samples are matched as pairs across the files. Declare the margin you are willing to accept, and it runs both one-sided tests and reports the confidence interval against that margin. Paired (same samples measured twice) or unpaired, Welch or pooled. It gives **three** answers, not two: equivalent, a real difference, or **inconclusive** &mdash; the case people routinely misreport as "no significant difference, therefore the same" &mdash; and for an inconclusive result it says how many results per method would settle it. Downloads as a CSV, and joins the audit package when one is exported.
11. **Watches batches against a golden envelope** (the "PCA & multivariate SPC" tool). Load a campaign of time-series readings &mdash; batch, hours in, and several sensors &mdash; nominate the runs you were happy with, and it learns the path they followed and scores every batch against it. **Hotelling's T&sup2;** collapses all sensors into one number: how far this moment sits from the middle of normal. **Q** asks a different question: whether the sensors still relate to each other the way they normally do, which is how a drifting probe shows up while every individual reading is still in range. Alarm limits are calibrated on reference batches **held out of the model that scored them**, so "99%" means a batch the model had never seen. Output names the hour an alarm began and the sensor furthest out, with the golden envelope drawn behind the batch's own trace.
12. **Splits a spread into named sources, and qualifies the method that measured it** (the "Variance components, ANOVA & Gage R&R" tool). Two questions out of one piece of arithmetic. *Where is the variation coming from?* takes repeated measurements labelled by the source you suspect &mdash; resin lot, analyst, vessel, shift &mdash; and splits the total spread into real between-group differences and the scatter of repeat measurements on the same group, then names which pairs genuinely differ using **Tukey's method**, which holds the confidence across every comparison at once rather than one pair at a time. A negative variance estimate is reported as zero and said out loud, rather than quietly hidden. *Can my measurement system see it?* runs a crossed **Gage R&R** on a balanced samples &times; operators &times; repeats study: repeatability (the instrument), reproducibility (the people), and genuine part-to-part differences, judged against your specification window rather than against the samples you happened to pick, plus the number of distinct levels the method can resolve. An unsupported part-by-operator interaction is pooled back into error, which is standard practice and is stated in the output. This matters before anything else here: a capability index, a trend report and a comparability study all take the measurement at face value, and if a third of what you observe is the assay then a third of each of those numbers is about the assay.
13. **Says which specification limits the data can defend, and how big a study needs to be** (the "Tolerance intervals, power & sample size" tool). A **tolerance interval** is the honest version of "mean plus three standard deviations": it covers a stated share of future production with stated confidence, and because the standard deviation is itself estimated, the factor is larger than people expect &mdash; on ten results, covering 99% needs about **4.4**, not 3. Give it the limits you already hold and it says whether this data supports them, and if not, whether more results would fix it or **no sample size ever could**, which is the answer that saves the most time. Normality is **tested** (Anderson&ndash;Darling) rather than assumed, because a specification is a claim about the tails, which is exactly where the wrong distribution bites. Run backwards, the same machinery sizes a study before instrument time is booked: equivalence (TOST), a two-group difference, or one group against a target, with the power curve and a table of what each study size actually buys. The calculations are exact and t-based, not the normal approximation that quietly overstates power at development sample sizes.
14. **Designs screens and formulations, not just factorials** (in the DOE builder). A **definitive screening design** (Jones &amp; Nachtsheim) screens 3 to 14 factors in about twice their number of runs, and unlike a Plackett-Burman screen its main effects are orthogonal to **every two-factor interaction**, so a large reading cannot be an interaction wearing a main effect's name. Every factor also runs at its middle setting, so curvature is estimable &mdash; the screen can tell you the best setting is *inside* your range, which a two-level screen is blind to by construction. The conference matrix behind it is built by Paley's method and its defining property is **verified before the design is issued**. Three **mixture designs** (simplex lattice, simplex centroid, extreme vertices with real minimum and maximum percentages) handle formulation work, where components are shares of one blend and cannot be moved independently; amounts are rounded so each run sums exactly to the batch total. The finished run sheet is fitted with a **Scheffé blending model**, which correctly has no intercept, and cross terms are reported as synergy or antagonism. Where component limits mean a pure-component blend was never formulable, the tool says so rather than quoting an extrapolated coefficient as a prediction.
15. **Routes you from a plain-English description** (the box at the top of the page). Type "purity jumps around between resin lots and I cannot tell if it is the assay" and it names the tool, the mode, what data to bring, what the tool will tell you, and what to do next &mdash; then takes you there with the mode already selected. It shows the words it matched on, so you can see why, and when two tools are close it **asks the one question that separates them** instead of guessing. Nothing it does not recognise is answered with a guess: it says nothing matched.

    Deliberately **not** a language model. It matches a lexicon of phrases and everyday concepts you can read in `advisor.js`, so it is instant, deterministic, works offline, and what you type never leaves the page. Its accuracy is **measured, not claimed**: `advisor-eval.js` ships 129 labelled examples in two sets &mdash; phrasings built from its own vocabulary, and phrasings written deliberately avoiding that vocabulary &mdash; and the "how this works" panel computes the score live from them. At the time of writing that is **100% on the first set and 77% on the second**, with the honest caveat that the second set has since been used to find faults and so is no longer a clean test. The file is there for you to add your own phrasings to.
16. **Draws the protein, and the hairpin** (in the sequence optimizer). The promise of codon optimization is that the gene changes and the protein does not &mdash; one line to assert and hard to take on trust, so it is **drawn**: every residue as a coloured box by chemical character, with the codon encoding it underneath, marked where the codon changed. Hover any residue for its codon and how strongly the host favours it. A Kyte&ndash;Doolittle hydropathy trace runs above it.

    Separately, **"no hairpins near the start"** is available as a *hard* requirement, not a trade-off: a stem of N or more Watson&ndash;Crick pairs closing over a loop of 3 to 8 bases, anywhere in the first N bases. Structure there holds up ribosome loading, so one hairpin can cost more expression than a poor codon further in. A sequence that still has one never wins, whatever its CAI &mdash; and because the start codon is fixed and few codons follow, if it cannot be cleared the report **says so** rather than dropping the requirement. The hairpin is drawn as a base-pair diagram before and after: circles for bases, rungs weighted by hydrogen bonds, the loop turning the corner.

    There is deliberately **no free energy** in that figure. A number in kcal/mol needs a nearest-neighbour parameter set and a partition function; printing a plausible-looking one from anything less, beside a diagram that looks like the real thing, would be worse than printing none. Nor is the protein drawing a structure: nothing here folds a protein, and nothing offline could.
17. **Reports several models, not just the winner.** The leaderboard already scores a dozen; now the top three are each **refit and asked independently which inputs they lean on**, and their answers are shown side by side with a measured verdict on whether they agree. Three model families that work in completely different ways landing on the same driver is far better evidence than any one of them alone &mdash; and where they disagree, the tool says so plainly rather than letting one ranking stand unchallenged. A driver only one model likes is reported as a lead, not a finding.
18. **Teaches the concepts.** `learn.html` (ML Agent Academy) has 38 interactive lessons, each with an analogy, a hands-on visual and a quick check. Examples: grow a decision tree and watch it carve up the data, send a batch through five trees of a random forest and see them vote, step through k-means, drag the boosting rounds, see design shapes (factorial cube, central composite, Box-Behnken), and turn noise up on a Pareto chart.

19. **Picks the vector for a programme that has not started yet** (the "Plasmid & vector selection" tool). Four steps, no sliders. **1** Load what you have already screened &mdash; Excel, CSV or JSON &mdash; one row per construct, with the protein it was for as well as the parts it was built from. **2** Load the factors and levels you can actually order, so the tool never proposes a promoter you cannot buy; levels can be semicolon-separated in one cell or one per row, and a continuous factor takes a Min, Max and Step. **3** Load the incoming programme's protein attributes, one row per programme, so a whole quarter's intake plans at once. **4** Out comes a run sheet per programme: which vector to build, its predicted titer with a calibrated interval, which rows reach past your evidence, and a column to write the measured result into. It downloads as a CSV.

    **Three ways into every step, and one parse path.** Upload a file, paste a block, or type it in. Pasting works straight off a spreadsheet copy, which arrives tab separated rather than comma separated. Step 2 has a small builder, because a catalogue is usually three or four lines and faster to type than to find &mdash; and a **Suggest from the history** button fills it from the columns your runs already contain, so the levels it offers are ones you have actually used; you then delete what you cannot order today, which is often less than what was run last year. Step 3 builds a programme at a time, and once step 1 is loaded the form asks for **exactly the protein attributes your history records**, offering the values it has seen, with an explicit escape hatch for a molecule unlike anything before it. Offering the real levels is not a convenience: a mistyped protein class reads downstream as "a value the historical runs do not contain" and correctly marks the programme untested, which is a maddening way to find a spelling mistake. There is deliberately no hand-entry form for step 1 &mdash; nobody types two hundred runs. Pasted, typed and uploaded data are all turned into the same table and handed to the same function, and that equivalence is asserted in the tests rather than assumed, because two parse paths would drift and the symptom would be a catalogue that behaves differently depending on how it arrived.

    **Excel is read in the browser.** An .xlsx is a ZIP of XML, and both halves are already there: `DecompressionStream('deflate-raw')` inflates the entries natively and the XML is machine-written and regular enough to scan. So nothing is installed, nothing is uploaded, and a workbook with the runs on one tab and the catalogue on another is read once with the right tab chosen. Three things in that reader are easy to get quietly wrong and so are tested directly: a row that **skips cells** (a reader pushing values in file order puts the titer in the promoter column and shifts everything after it &mdash; plausible-looking and completely wrong), a **date**, which Excel stores as a number with a format and an unaware reader hands back as `45730`, and Excel's **phantom 1900-02-29**, a day kept for bug-compatibility with Lotus 1-2-3, which means serials at or below 60 sit on a different epoch from everything above them.

    The sheet is a **design, not a top-twelve list**. Every level of every factor appears as near equally often as the run count allows, because a sheet that ran your strongest promoter eight times and the weakest once cannot tell you anything about the weakest however good its numbers look. It also gives **two recommendations** and says when they disagree: the highest central estimate, and the highest *lower bound* &mdash; the build least likely to disappoint. If one shot is all you get, the floor is usually what matters.

    **The honesty this tool turns on is about the protein, not the vector.** A promoter the corpus has not used can be mapped to the nearest one that has, and said so. A *protein* cannot be treated that way: if every historical run was a monoclonal antibody, the data holds no information whatsoever about how a bispecific responds to a promoter choice &mdash; and the arithmetic will not complain. A model fitted on one molecule returns a confident number for another, and the conformal interval stays **narrow**, because nothing in the residuals knows the question changed. So transferability is measured before anything is predicted: how many distinct proteins the history actually contains, which protein attributes vary at all, and whether the incoming molecule sits inside that. A history of one protein is told it cannot speak for another. An attribute every run holds fixed is reported as carrying no evidence. A protein class nothing has ever run is **refused** rather than mapped to the nearest molecule and scored. Two molecules is reported as *thin*, not *supported*, because a protein effect fitted on two points is a line through two points.

    A factor in your catalogue that the historical runs never recorded is named and left out of the choice rather than picked blind, and a record-keeping column in the programme sheet (Notes, Owner, Target_Date) is read as record-keeping &mdash; keeping one would make it look like a protein attribute the history has never seen, which flips a well-supported programme to untested on the strength of a scheduling note. The original slider desk and the paste-a-sheet forecaster are still there, folded away under the flow, because the interval machinery beneath them is the same and its coverage is what the tests measure.

20. **Says how wrong it might be** (throughout the main agent). The agent used to be confident in a way its own arithmetic did not support: a cross-validated R&sup2; quoted to three decimals off forty rows, a driver ranking with no sense of how much it would move if the dice fell again, and point predictions with nothing attached but a dataset-wide RMSE. None of those is a wrong calculation. All three invite a reader to act on a number far firmer than the evidence. Three separate quantities now travel with the result, kept separate on purpose because rolling them into one "confidence" score is how this usually goes wrong.

    **How wrong a prediction can be.** The what-if desk showed &ldquo;typical error &plusmn; RMSE&rdquo;, which was the most reassuring thing the page could have said and the least defensible: one number for the whole dataset cannot widen, so it was at its most confident exactly where it was least justified. It is now a **split-conformal interval**, calibrated on rows held back from a second fit, that widens with distance from the data. Measured on a corpus with deliberately heteroscedastic noise, a fixed 1.96&sigma; band covered **93.2% of runs inside the data and 35.0% outside it**; the conformal band at the same nominal 95% held **95.1% and 100%**, widening 5.6 times to do it. Coverage is **approximate rather than guaranteed**, and is reported that way: the final model is refit on every row while the band comes from a model fitted on part of them, so the two are not perfectly exchangeable &mdash; on 300 rows a single 90-row calibration slice landed between 91.1% and 97.8% across four corpora, and on 4,000 rows it settled at 94.0% against the 95% asked for. The slice size is shown next to the band, and where the slice cannot resolve the tail being asked for (it reaches at most nCal/(nCal+1)) the band is labelled a floor rather than a guarantee.

    The desk's sliders stay inside each input's own observed range, so the warning is not about one setting going too far &mdash; it is about **combinations the data never contains**. Every input in range individually, the joint position unobserved. On the shipped Protein A capture sample the worst reachable corner sits 1.88 normalised distances from the data, which trips the amber *edge of the data* badge and widens the band from 86.9&ndash;89.2 to 89.1&ndash;94.0 &mdash; from 2.4 points wide to 4.9. A fixed RMSE is identical at both.

    **How firm the score is.** An R&sup2; is itself an estimate, and on small data a wobbly one. Resampling the held-out predictions costs nothing &mdash; no model is refitted &mdash; and turns a bare score into the range the data can support: on 30 rows the 95% range spans about 0.13, tightening to 0.02 by 600 rows (on the shipped capture sample, 160 rows: R&sup2; 0.785, and the data cannot separate that from anything between 0.722 and 0.830). Where that range is wider than 0.25 the tool says plainly that the leaderboard order is largely noise and comparing models on these rows will not reliably say which is better. Below about 10 rows per input it says so, and notes that cutting inputs is usually faster than collecting rows.

    **Whether the driver ranking is real.** Permutation importance is a random quantity. The agent already averaged three shuffles and discarded the spread; keeping it puts **whiskers on the driver chart** and lets the tool say whether the top driver is genuinely clear of the second or whether they are joint leaders whose order a second run could reverse.

    That raised a trap worth naming, because the obvious test for &ldquo;does this bar mean anything&rdquo; is **wrong and measurably so**. Importance is read off the rows the model was fitted on, so a model leans on any column it is handed, signal or not. Three columns of pure random numbers scored **0.005 to 0.007 against standard errors near 0.002** &mdash; &ldquo;significant&rdquo; by their own spread and completely meaningless. So the reference is not zero. It is measured: shuffle the target so there is nothing left to find, refit, and ask the same model again. Anything at or below that **blank** carries no evidence. On the shipped Protein A capture sample two of five inputs fall at or below it when the target is step yield &mdash; and one of those, wash conductivity, becomes the **top** driver at 76% when the target is switched to purity. The blank is not a property of the column; it is a property of the question. And because the whiskers cover only the shuffling noise and not the variability of having sampled these rows rather than others &mdash; measured at **1.5 to 5.7 times larger** &mdash; the tool labels them as the most favourable reading of how firm the order is, rather than the whole story.

21. **Starts from your job, not from the method** (the panel above every tool). The selector names techniques &mdash; tolerance intervals, TOST, PCA &mdash; which is right for somebody who already knows which one they want and wrong for everybody else. Nobody arrives looking for &ldquo;variance components&rdquo;. They arrive because purity moves between resin lots and nobody can say whether it is the resin or the assay. So the **Where this can be used** panel offers four department workbenches &mdash; **upstream bioprocessing**, **regulatory &amp; technical writing**, **QA &amp; deviation management**, and **business development** &mdash; each listing concrete jobs, and each job saying four things: which tool it opens, what data to bring, what comes back, and **what the tool will not do**. One click lands you on the right tool, with practice data already loaded where a dataset fits.

    That fourth field is the reason the panel exists, and it is rendered in red next to the other three rather than tucked into a tooltip. Two of these departments want documents written, and **this page cannot write a document** &mdash; there is no language model here, which is exactly why your data never leaves the browser. So the regulatory bench opens by saying so, and then does the thing that is actually worth something: it names which tool produces which section's numbers (shelf life from the Q1E confidence limit, method transfer from TOST with *inconclusive* available as an answer, a specification defended by a tolerance interval or shown to be indefensible at any sample size) and which export carries the audit trail a reviewer will ask for. The business-development bench says it will not build your deck, and points instead at the capability claim a technical buyer will push on &mdash; including when the data does not support the number you were hoping to put on a slide. The QA bench will not assign root cause or decide disposition; it replaces &ldquo;review the whole batch record&rdquo; with &ldquo;start at hour 14, look at the dissolved oxygen probe&rdquo;.

    `departments.js` is plain content, meant to be edited to match your own org chart, and it is held to its promises by the tests rather than by review: every job must route to a tool the selector actually offers and a practice dataset that actually exists, every job must carry a substantive *will not*, and no field anywhere may promise to draft, write, assemble or format a report, protocol, deck or narrative. That last guard is asserted in both directions &mdash; the five phrasings a later edit would plausibly add must be caught, and the refusals the benches are required to carry must not trip it &mdash; because an earlier version of it required the noun to sit directly after &ldquo;your&rdquo;, and &ldquo;it drafts your technical development report&rdquo; walked straight through.

22. **Practice datasets are biologics only, grouped by the function that would use them.** The built-in sets used to tour unrelated industries &mdash; injection molding, loyalty tiers, customer segments &mdash; which made the tool read as a generic demo and left a downstream engineer with nothing to click that resembled their own work. There are now nine, every one a biologics development or manufacturing dataset, each tagged with its function and shown under that heading: **clone screening** and **clone phenotypes** (cell line development), a **fed-batch 2&#8308; factorial** (upstream PD), **Protein A capture** with yield and purity pulling against each other (downstream PD), a **formulation screen** on aggregation after four weeks at 40&nbsp;&deg;C (AFS), **scale-up** across two sites and three scales (MSAT), **batch release pass/fail** (GMP manufacturing), **batch disposition** in four ranked outcomes from Reject to Release (QA), and the **bioreactor log joined to the densitometer report** (QC). Whichever function you picked in *Where this is used* floats to the top and is marked as yours.

    Each one is generated from a fixed seed with a real, findable structure, because a practice dataset with nothing in it teaches the wrong lesson about what the tool can do &mdash; and the structures are chosen to teach something specific. The fed-batch design carries a **temperature-by-feed interaction**, so a feed that helps warm hurts cool. The formulation screen has a **pH optimum away from both edges**, which a two-level screen is blind to by construction. The capture runs make **yield and purity pull against each other**, which is what the multi-result optimiser is for. The scale-up set is deliberately **confounded**: kLa falls as the vessel grows and that is what costs titer, but Site B happens to run the big vessels more often, so a careless read blames the site &mdash; the tool is asserted in the tests to put kLa first. The disposition set has **ranked outcomes**, so *what moves a batch up a tier* is a real question, and its answer is operator experience and hold time rather than the production line, which is usually the opposite of what the room expects. And the clone screening set demonstrates the **leakage guard**: its day 3 reads and specific productivity are measured results, so they are set aside as inputs by default and re-including them deliberately is the exercise.

    Both the function tag and the declared target column are checked by the tests, because a practice dataset pointing at a column it does not produce fails in front of whoever trusted it first.

23. **Tabs, one job each** (four of them now, since the loop got its own). The page drifted. Every time something useful was added &mdash; the plain-English front door, the department workbenches, the *Where this is used* panel, nine practice datasets &mdash; it went in above the tool, and the thing people came for ended up below three screens of material they had already read once. **Tools** carries the technique selector and all nine techniques, and nothing else. **Where to start** carries the two things that help you choose one: *describe what you are trying to find out*, and *where this can be used*. **Practice data** carries the nine datasets on a page of their own, laid out as one grid rather than a grid per function: seven of the nine functions hold a single dataset, so headings gave each of them a row with two thirds of it empty. The function moves onto the card instead, the cards stay ordered so a function's datasets sit together, and whichever function you picked still comes first and is marked &mdash; so nothing is lost except the gaps.

    Moving the datasets off the tool page also left somebody arriving with nothing to load and no visible way to reach them, which is a dead end created by a tidy-up. The invitation beside the drop zone is that route, and it occupies the 360px the datasets used to, so it earns its place twice; it clears once data is loaded, because by then the invitation has been taken. The page itself is wider on a large screen &mdash; capped reading width is right for prose, and the lede and explanatory paragraphs carry their own, but tables, run sheets and card grids were being squeezed into a 1120px ribbon with 400px of margin either side.

    Everything that routes to a tool goes through one function, so the front door (which routes by setting the URL hash), the department job buttons, the practice datasets and the privacy lock all land on the Tools tab without each needing to know pages exist. Clicking a practice dataset loads it *and* carries you across, because leaving somebody on a page whose button just did something invisible elsewhere is the worst of both layouts. Every tab is linkable: `#where-to-start`, `#practice-data`, or a tool's own id such as `#variance`.

    The split is asserted in the tests &mdash; each block must be on the one page it belongs to and on no other, every tool in the selector must have its panel on the tool page, every page declared in the script must exist in the markup with a tab to reach it, and nothing may sit outside all three &mdash; so the next addition has to choose a side on purpose rather than landing on top of the tool by default. The tool page was also tightened: the hero was set at poster size with a 2.3rem headline above step 1 while a one-line description of the same tool sat in the strip above it, so the heading is compact, the duplicate line is kept for screen readers but not drawn, and step 1 now starts 324px down instead of 527px &mdash; above the fold on a laptop and on a phone. No horizontal scroll at any width from 320px up.

24. **The data is shown as a table before the model runs.** Step 2 used to show a column profile &mdash; type, role, missing, distinct, range &mdash; which answers *what did it make of my columns*. It does not answer *did my file load correctly*, and that is the question somebody actually has at the moment they press the button. A row shifted by a stray comma, a header read as data, a date column that arrived as numbers: all obvious in a table of rows and invisible in a summary of columns. So the rows themselves now sit above the profile, with the column names shown **exactly as the file has them** (the table style upper-cases headers, and a column called `Day3_VCD_e6` displayed as `DAY3_VCD_E6` is not the column in the file), blank cells marked as blank rather than rendered as nothing, sticky headers, and a footer giving columns &times; rows and the total cell count. Capped at 100 rows, because this renders on the load path and a 40,000-row table would freeze the tab for rows nobody scrolls to &mdash; a file shorter than the cap says &ldquo;all 12 rows&rdquo; rather than claiming to be truncated. Measured on a 40,500-row paste: 2.9 seconds from paste to a drawn preview, the page still responsive, no horizontal scroll.

25. **Capability figures that depend on a bell shape are withheld when the data has not got one.** Cp and Cpk are ratios of distances to spread and stand whatever the shape. The expected PPM, Z.bench and sigma level are different: every one of them is a normal tail probability, and a tail probability from the wrong distribution is not approximately right &mdash; it is wrong by orders of magnitude. Measured on a right-skewed impurity with the limit at its true 99.9th percentile, so the real rate is 1,000 PPM by construction: at a skewness of 0.65 the normal figure reads **62 PPM**, sixteen times under; by a skewness of 1.8 it reads **0**. Normality is now tested with the same Anderson&ndash;Darling the tolerance tool uses, the tail figures are withheld rather than labelled approximate when it fails, and what remains is named &mdash; Cp and Cpk, and the observed count out of spec, which needs no distribution at all. The warning this replaced fired on a skewness above 1, so it stayed silent through the first of those cases: the mild right skew that impurities, aggregates and particulates actually have. Too few rows to test is reported as untested rather than as a pass.

26. **DOE effects are judged after correcting for how many were tested.** Every term in a designed experiment is its own hypothesis test, and a 2&#8308; design fits eleven of them. Each p-value is calibrated &mdash; the per-term false positive rate measures at about 5%, as it should &mdash; but reading the list as *&ldquo;these effects are significant&rdquo;* is a different claim from any single test in it, and it is the claim people make. Measured over 500 analyses of a 2&#8308; design with three centre points and **no real effect in it at all**, 23.2% produced at least one term below p = 0.05, and 0.37 false findings on average: roughly one screening run in four hands back something that is not there.

    So effects are now reported on **Benjamini&ndash;Hochberg adjusted q-values**, with the raw p kept beside them in the table. On the same null data that drops the rate from 23.2% to **1.8%** of analyses, and on the same design carrying two real effects it still finds both **100%** of the time &mdash; so the correction costs no power here. BH rather than Bonferroni or Holm because a screen wants to control the share of claimed effects that are wrong, and the stricter corrections would strip real effects out of a nineteen-run design where power is already thin. The family-wise risk is also stated in plain numbers, because an adjusted column nobody reads does not stop anyone over-reading the raw one; it is given as an upper bound, since the terms share one error variance estimate and the measured risk (23.2%) sits below what independence predicts (43.1%). The findings, the next steps and the action plan all read the same adjusted column through one helper &mdash; two of them reading the raw one while the third reads the adjusted one is how a report ends up recommending a lever it has just disowned.

27. **The run sheet spends its wells where they are worth most.** A 48-well screen from a catalogue of 36 vectors used to come back as 36 rows, silently &mdash; the sheet simply stopped and nothing said why half a plate was missing. Sheets longer than the catalogue now replicate, and more importantly the default allocation changed. Measured over 4,000 simulated 48-well sheets drawn from 36 candidates, scoring how often the sheet identifies the truly best vector:

    | allocation | poor prediction | good prediction |
    |---|---|---|
    | 36 distinct &times; 1 | 33.1% | 36.4% |
    | top 16 &times; 3 | 41.9% | 48.4% |
    | top 12 &times; 4 | 41.4% | 55.9% |
    | top 8 &times; 6 | 37.2% | **61.4%** |

    Running everything once is the worst option in every column, because a single observation of a vector is mostly noise and a sheet of singles ends up ranking noise. How far to concentrate is read off the model's own cross-validated R&sup2; rather than guessed, so a model that cannot predict spreads wider because its ranking deserves less weight. The cost is stated rather than hidden: concentrating gives up the level balance that lets a sheet estimate factor effects, which is the right trade for *which vector do we build* and the wrong one for *what drives titer* &mdash; so the sheet has both modes and the screening one still balances.

    **Categorical helper factors** work as they arrive: a catalogue of six helper plasmids at four to six levels each, with no Min or Max anywhere, parses and enumerates &mdash; 5,760 buildable vectors from a realistic AAV-style catalogue, scored in full rather than sampled. That became affordable by fixing the nearest-neighbour search behind the intervals, which built and sorted an array of every training distance on every call: partial selection of the five nearest instead took 4,000 scored candidates from **2,600ms to 36ms**, and the conformal coverage tests confirm the answer is unchanged.

28. **The loop: passive data, a design, runs, back into the model, again until it is good enough.** Four of the five steps already existed separately &mdash; a baseline from operational data, a recommended design, a run sheet with a column to write results into, and a model that can be refitted. What was missing was the loop: nothing stacked a round of results onto what came before, nothing tracked whether the model was improving, and nothing would say when to stop. Step 6 of the agent does all three. Rounds are matched **by column name**, so a sheet that comes back with its columns reordered and an extra one added lands in the right places rather than putting operator initials in the titer column.

    **The obvious way to measure progress is wrong, and the brief asks for it.** R&sup2; is error measured against the spread of the data, and every round of a DoE campaign widens that spread deliberately &mdash; that is what the design is for. Measured on identical data, identical noise and an identical model, widening the sampled range alone takes R&sup2; from **0.376 to 0.975 while the cross-validated RMSE sits at 0.265 the whole way**. A campaign steered by R&sup2; would declare success after one round of widening ranges having learned nothing. So progress is tracked on the **prediction interval** and the **RMSE**, which do not move when the range does, and every R&sup2; change is split into the part the widened spread explains and the part a genuinely better model explains. On a worked two-round campaign that split came out as +0.470 from range against &minus;0.006 from the model.

    **What another round would buy is measured, not promised.** The model is refit on subsets of increasing size to trace the curve this dataset is actually on, then read forward. Validated against what actually happens: projecting the error at double the sample size landed within 5&ndash;13%, erring conservative, and the estimated noise floor came out at 0.322 against a true 0.300 &mdash; which is the number that says stop running plates and improve the assay instead. Two guards matter: the fitted slope cannot be negative and the projection cannot be worse than what is already measured, because an unguarded least-squares fit on noisy subsample points will cheerfully predict that running more experiments makes the model worse.

29. **Variance inflation, and the full Nelson rule set.** Two gaps from the specification, both small and both worth having.

    **VIF** regresses each input on all the others at once, which catches what a pairwise correlation cannot: inputs that are each only mildly correlated but jointly almost determine one another. On a worked case where `C = A + B + noise`, the largest pairwise |r| is **0.696** &mdash; nothing trips a 0.9 threshold &mdash; while every VIF lands between **16 and 32**. Validated against the identity VIF = 1/(1&minus;r&sup2;) rather than against itself: at r = 0.95 theory says 10.26 and it measures 10.10. What it costs you is precision on a coefficient, not predictive accuracy, and the tool says so: a model full of collinear inputs can predict perfectly and still be unable to say which input to change. Exact collinearity does not fail cleanly &mdash; inverting a singular matrix returns enormous numbers rather than nothing &mdash; so a VIF in the billions is reported as **inseparable** instead of as 621,657,757,936, which would be the honest output of the arithmetic and useless to everybody.

    **The control chart runs all eight Nelson rules**, not the three it had. Rule 1 catches a point too far out to be chance; the other seven catch what a limits-only chart is blind to, which is a process that has shifted or drifted while every point stays inside the lines. On a 0.9&sigma; shift the limits chart raises one signal and the full set raises twenty-five. Each rule is tested on data built to trip exactly it, using the sigma the chart itself computes.

    That sensitivity has a price, and it is measured rather than hidden. On 3,000 in-control series the 3&sigma; rule alone raises a false signal about once every **367** points &mdash; the textbook figure is 370, so the implementation is calibrated &mdash; and the full set about once every **50**. On a fifty-run chart that is roughly one false signal expected per chart from a process with nothing wrong with it, so the number is reported beside the signals and the rule set is a choice. The conservative mode is quoted at its real rate of one in 103 rather than at rule 1's nicer 367, because that mode also runs the moving-range chart and it fires on its own account.

30. **JSON in, and text columns with more levels than one-hot can carry.** Two more gaps from the specification.

    **JSON loads like a CSV.** A LIMS or an instrument rarely hands you a CSV, and the shape it hands you varies: a list of records, a records list wrapped in an envelope of metadata, one record per line from a streamed export, one array per column from a dataframe, or a list of rows with the names on top. All five are recognised and the page says which one it read, so a file pulled from the wrong endpoint is obvious rather than silently half-read. A nested object takes dotted column names (`qc.purity`), a list inside a single record is kept as text rather than invented into columns, `null` reads as missing rather than as zero, and a field only some records carry still gets a column with blanks where it is absent &mdash; rather than knocking every later value one place to the left. A `.json` file that is not JSON says so instead of arriving as one column.

    **Many-levelled text columns are carried as numbers, not collapsed.** This is the 48-strain case, and the helper-plasmid catalogue, and any supplier or operator list. One-hot encoding gave the twelve commonest levels a column each and lumped the rest into &ldquo;other&rdquo;, so a column separating 48 strains arrived separating thirteen, and the thirty-six it dropped were indistinguishable from each other in the output. Each level now carries two numbers instead: **how common it is**, and **how the result averaged for it**, pulled towards the overall average with a weight of ten prior observations so a level seen twice cannot claim its own two runs as the truth. Measured over eight datasets of 200 runs across 40 strains where the strain genuinely matters: **R&sup2; 0.70** against **0.49** for the collapsed version. A fifth of the achievable fit was in the levels one-hot was throwing away.

    The level average is also the one encoding here that can leak the answer, so it is rebuilt inside **every cross-validation fold** from that fold's training rows alone. The cost of getting that wrong is measured, not asserted: on a column that is pure noise with nothing in the data to predict at all, rebuilt per fold it honestly scores **R&sup2; &minus;0.16**, and fit once on every row the same nothing scores **+0.15** &mdash; a working model that does not exist. The split-conformal intervals in the vector tool depend on the same discipline, since the encoder is now fitted on the model's rows and never on the calibration slice.

    What smoothing cannot remove is thinness; it only makes it gradual. So the vector tool's coverage panel gained a second class beside *never run here*: levels whose own runs carry **less weight in their own number than the prior does**, named with the run count and the weight &mdash; &ldquo;pHelp-13 (8 runs, 56% of its number is the overall average)&rdquo;. They can be ranked; a small difference between them is not evidence. The audit trail records which columns were encoded this way, because an importance or a coefficient for one of them is a frequency and a smoothed average, not a level switch, and a reviewer has no way to know that unless it is written down.

31. **A playbook per function, and the two methods those playbooks kept needing.** The *Where this is used* panel answered "what is this technique for". It did not answer the question somebody actually arrives with &mdash; *I run this group, what do I do first, what will it buy me, and where will it let me down* &mdash; which needs three things a list of uses leaves out: an **order**, the **measured cost of skipping a step**, and the **gaps named out loud**. Pick your function and all eight now carry one: cell line development, upstream, downstream, analytical and formulation, MSAT, GMP manufacturing, QC, and QA and regulatory. Each opens with the one thing to do first and why it comes first &mdash; which for five of the eight is *qualify the measurement before you trend its output*, because a capability index built on an unqualified assay is a confident number about the assay. Every step names the tool, what it does, a measured figure where one exists, and where it stops; every playbook ends with what the tool will **not** do for that group. A step with a "measured" claim and no number in it fails the build, which caught four of my own paragraphs that were describing a mechanism and calling it a measurement.

    **Attribute agreement, with kappa.** Gage R&amp;R answers "can the measurement see it" for a *measurement*. It cannot touch a **judgement** &mdash; a visual inspector calling a vial accept or reject, a plate read, a defect grade &mdash; because there is no number to take a variance of, and that is a large share of pharmaceutical quality work. So: within-appraiser repeatability, appraiser against appraiser, and each appraiser against a known standard, with **Cohen's and Fleiss' kappa** beside every agreement percentage and 95% intervals bootstrapped over samples rather than taken from an asymptotic formula that is fragile exactly where these studies live. The reason kappa is not optional, measured: with a **10% defect rate, an inspector who simply passes every vial scores 90% agreement, a kappa of exactly 0, and a 100% miss rate**. The percentage alone reads as an excellent inspector. For a binary call the two error directions are reported separately, because they are not symmetric &mdash; a miss reaches the patient, a false alarm costs yield &mdash; and a single agreement figure hides which way an appraiser leans. The first version of this refused to analyse the rubber stamp at all: it took the categories from the calls alone, and an inspector who only ever says "accept" gives one category, so the one analysis that exposes them was the one that would not run. That regression is now a test.

    **Charts for things you count**, with overdispersion measured rather than assumed. c, u and p charts, because a counted series on a measurement chart gets the limits wrong: a Poisson count's standard deviation is the square root of its own mean. But the choice of chart matters far less than this &mdash; the textbook limits assume every vial carries the same underlying rate, and real counts cluster by lot, line and shift, so the spread is wider than the square-root law allows. Measured over 400 charts of 60 points at a mean of 16: at a dispersion of **3**, ordinary for particle counts, the textbook chart flags **one point in sixteen** from a process behaving perfectly &mdash; about four false signals per chart &mdash; and at a dispersion of 5 it flags **one in eight**. Laney's correction brings those to one in 94 and one in 61. When the counts really are Poisson the correction comes out at **&times;1.05**, so it costs nothing when it is not needed, and the dispersion estimate itself is accurate (1.00, 1.97, 2.97, 4.88 against true 1, 2, 3, 5). The honest other side is reported too: widening costs sensitivity, catching a 60% sustained rise on 71% of charts against the textbook chart's 100% &mdash; which is not a fair hundred percent, since that chart is flagging one point in sixteen anyway.

    Still missing for counted work, and said rather than left to be discovered: no **rare-event chart** (units or days between events), which is the right tool at a reject rate in the tenths of a percent and which a proportion chart cannot replace; no CUSUM or EWMA; and no non-normal capability or distribution-free tolerance bound, so for skewed data the defensible answer remains Cp, Cpk and the observed count out of spec.

32. **Three more functions, and the two ways out of a failed normality test.**

    **Eleven functions, not eight.** Facilities &amp; engineering, microbiology &amp; environmental monitoring, and the Particle Core (PCC) join the list, each with unit operations for both modalities, a line per technique, and a full playbook. AFS gained mass spec: intact and subunit mass, peptide mapping and modifications, and host cell protein. GMP manufacturing, MSAT, AFS and downstream PD were already there &mdash; the four-item list people were seeing is the separate *Start from my job* panel, which carries workbenches rather than functions.

    Two of the new three exist mainly because their data breaks the usual defaults. Microbiology is **counted, rare and judged by eye**, which breaks the measurement chart, the bell curve and percent agreement all at once. Facilities data **drifts** rather than exceeding a limit, which is what the extra control-chart rules are for, and cleanroom particle counts are bounded at zero with a long tail, which is what the next item is for.

    **Capability on data that is not bell-shaped (Box-Cox).** Withholding the tail figures when the shape is wrong is correct, and it is still a dead end: a QC group that has to write a specification this week is left with Cp, Cpk and a count. So where the shape can be fixed, it is: Box-Cox picks the power that maximises the profile likelihood, the specification limits are transformed the same way, and the tail is computed there. The discipline that makes it honest is that **normality is tested again on the transformed values** and the figures stay withheld if the transform did not work. Measured on a right-skewed reading whose limit sits at its true 99.9th percentile, so the real rate is **1,000 PPM by construction**: the straight normal fit reports **0 PPM** &mdash; no risk at all &mdash; and the transformed fit reports about **1,300**, with &lambda; landing on 0, the log, as it should for lognormal data. On a bimodal reading the transform is fitted, fails its re-test, and the figures stay withheld: no power of a two-humped variable is bell-shaped, and a transform that failed is not a licence to report. Data that passed its original test is never offered a transform at all, so there are never two sets of tail figures to pick the friendlier one from.

    **A tolerance bound that assumes no distribution.** Sort the results and the share of the population below the j-th one follows a Beta distribution that depends only on n &mdash; skewed, bimodal, bounded at zero, it does not matter, because only the ranking is used. What it costs is sample size, and the cost is steep: a one-sided 99% claim at 95% confidence needs **299** results from the ranking alone, against about ten for the normal-theory factor; two-sided needs **473**; a 95% claim needs **59**. All three match the published values exactly. Coverage is verified empirically on three shapes that break the normal factor &mdash; lognormal, exponential and uniform &mdash; by asking how often the bound really does sit above the population's 99th percentile. Below the required count it refuses and states the confidence the data actually reaches: **thirty results reach 26%, not 95%**, with the 299 attached so the answer is actionable rather than just negative.

    Both are reported beside the normal-theory answer rather than instead of it, so the trade &mdash; assume a shape and need ten results, or assume nothing and need 299 &mdash; is made with open eyes. Three playbook gaps that claimed this work did not exist were corrected in the same change, since they had become false.

33. **The two guidance panels became one.** *Start from my job, not the method* and *Where this is used* asked the same question &mdash; which group are you in &mdash; in two different selects, and then answered two halves of it in two places. Worse, the method you had just read about was reachable only by going back to the technique selector and hunting for its name, which is exactly the problem the first panel existed to solve. Now there is one **Where this can be used** panel: pick your group once, and you get the **jobs** that group brings (each opening its tool, with practice data where a dataset fits), **every method with what it does for that group and a button that opens it**, the **playbook**, and the **unit operations** inside the function. Nothing was dropped in the merge &mdash; a department bench with no function of its own, such as business development, appears in the same picker under *Other ways in*, which the build checks, because a bench that quietly disappears is worse than two panels.

34. **A loop tab, and the stopping criteria read from your own run.** One pass answers a question; four passes change a process, and the method was only ever implied by the tool order. The **How to use this** tab draws it: a four-node closed loop &mdash; **Discover** (messy history in, drivers out), **Disentangle** (history is correlation, so it fills in the DOE that separates the factors), **Refine** (your new results go back in beside the old), **Converge** (intervals tighten, confounding untangles, screening gives way to response-surface work) &mdash; and highlights **the node you are actually on**, read from what is in memory. Each phase is a button that lands you on the right step of the right tool.

    The part worth building is underneath. &ldquo;Stop when the error plateaus&rdquo; is advice; **&ldquo;another 18 runs project 0.4% less error, so this one will not pay&rdquo;** is a decision. So the three exit criteria are computed, not printed: **the goal is met** from your own specification limits and the observed count outside them, **error has plateaued** from the campaign's own subsample learning curve, and **the process is capable** from Cpk against the 1.33 convention, which is named as a convention rather than a limit. Where a gate cannot be computed it says what is missing &mdash; usually that nobody has entered the spec limits &mdash; because a blank reads as a failure.

    Two defects found while building it, both the kind that pass every test and mislead in the browser. The plateau gate read a global the campaign panel never published and a `gain` field the projection never returned, so it would have silently reported &ldquo;needs two rounds&rdquo; forever; the panel now publishes its projection and clears it on reset. And a plateau projected from a **single** round was being reported as met &mdash; concluding that experimenting will not pay before one experiment has been run is precisely the wrong answer to hand somebody, so with one round it is labelled a forecast and the verdict is withheld. The loop cards also had to be renamed: `.phase` was already the DMAIC chip in the next-steps list, so they were restyling it.

    On the tool page itself, three words per pillar rather than an essay: **Learn &middot; Test &middot; Perfect**, one sub-headline about closing the loop, and a button through to the tab. The build checks each pillar stays eight words or under, that the diagram carries a text alternative, and that it uses no inline styles &mdash; the page's own security policy blocks those, so a `style=` on the SVG would render unstyled in a browser while passing every other check.

35. **The Particle Core, correctly.** PCC was built out as *process &amp; product characterization* on my own reading of the abbreviation, and it was wrong: it is the **Particle Core**. The label was the smallest part of the fix &mdash; the unit operations, the per-technique lines and the whole playbook described characterization studies and proven acceptable ranges, which is a different group's work entirely. All of it is replaced: visible inspection, subvisible counts by light obscuration, flow imaging and morphology classes, identification by FTIR, Raman and SEM-EDX, container closure and glass delamination, aggregation on stability, and the line and environmental contribution.

    This group is why the last two builds existed. Particle data is **counted, rare and judged by eye**, which breaks the measurement chart, the bell curve and percent agreement all at once, so the playbook runs: **attribute agreement** on the inspection first, because an inspector who passes every vial scores 90% agreement, a kappa of 0 and a 100% miss rate; then **count charts** with the clustering measured, since at a dispersion of 3 the textbook chart fires on one point in sixteen from a line behaving perfectly; then **capability** with the tail figures taken on a transformed scale, since the straight normal fit reports 0 PPM against a true 1,000; then **alert levels** from the ranking alone, which assume no distribution and need 299 results to do it; then the **drivers and the design** that separates what an investigation log has confounded.

    Named as still missing, because this is the group that would notice: no reading of a spectrum or a particle image, so FTIR and SEM-EDX identifications arrive as labels; no USP two-tier decision logic; no particle size distribution fitted across the bins; and above all **no rare-event chart**, which at a reject rate in the tenths of a percent is the one thing that would help most.

Ways to share results, all built in the browser:
- **Save as PDF**: an A4 report (action plan, what-if scenarios, every chart with its "how to read this" note, the DOE run sheet, the models in plain words, a glossary, and an audit trail).
- **Download Excel (.xlsx)**: every number behind the report, one sheet per topic (summary, audit trail, columns and roles, models, drivers, action plan, capability, control chart, desirability, DOE effects, what-if scenarios, DOE run sheet, data analyzed). Numbers stay numbers.
- **Download audit package (.zip)**: the PDF, the workbook, `audit-trail.txt`, the DOE run sheet, a README and `SHA256SUMS.txt`. The audit trail records the tool version, time, each input file's SHA-256 fingerprint, size and shape, the join (keys, unmatched IDs, averaged replicates), the target, settings and spec limits, every column set aside and why, the leakage check, the validation scheme, the models and the selection rule, the seed, the agent's log, the data-handling statement, and signature lines. It is decision support, not a validated GxP system.
- **Print** (clean, light-themed) and **Download as web page** (.html).

## Privacy guarantees

| Guarantee | How it is enforced |
|---|---|
| Data is never uploaded | Files are read with the browser's `FileReader`. All math is local JavaScript in this repository. |
| Nothing can be sent out, even by mistake | The page's Content-Security-Policy sets `connect-src 'none'`, `img-src data: blob:`, `form-action 'none'` and `default-src 'none'`, so the browser itself refuses outgoing requests. |
| The background thread is no exception | The sequence optimizer runs in a Web Worker. `worker-src 'self'` allows only this site's own `ga-worker.js`, and a worker inherits the page's policy, so it can reach no further than the page can. A test checks that the worker loads nothing but local files. |
| Nothing is stored | No cookies, local storage, IndexedDB or service worker. Closing the tab erases everything. |
| Deleted when you are done | **Finish and delete my data** wipes the data and every result from the page. It is also wiped after 30 idle minutes (on by default) and when you leave the page, so the back button cannot bring it back. |
| No LLM or AI service | The agent is classical statistics and ML plus written rules. There are no API keys or prompts. |
| No third parties | No CDN, analytics, ads or web fonts. Every file is served from this repository. |
| Stays true over time | `tests/run-tests.js` includes a privacy lint that fails CI if network, storage or tracking code is ever added. |

**Verify it yourself:** open DevTools → Network and run the agent, or press **Run privacy self-test** on the page. It deliberately tries to reach an outside server and shows that the browser blocks it.

**Fine print:** GitHub Pages, like any web host, logs that the page was opened. It never receives your data. Browser extensions can read any page you open, so use a clean browser profile for sensitive data. For the strictest setup, download this repository (or the intranet zip) and open `index.html` from disk with Wi-Fi off. It works fully offline.
